# HIR-0001 — 지휘(Opus)·구현(Sonnet)·검토(Sonnet) 역할 분담

- 상태: 실험 중
- 도입일: 2026-11-10 (v0.1.0)
- 도입 근거: 개발자 결정. 초기 하네스 운영 원칙은 "서브에이전트는 반복 문제가 확인된 뒤 추가"였지만, 개발자가 역할 분담을 처음부터 쓰기로 정했다. 실제 문제가 재현되기 전에 도입했으므로 아래 지표로 효과를 확인하고 유지 여부를 다시 정한다.

## 구성
| 역할 | 위치 | 모델 | 도구 |
| --- | --- | --- | --- |
| 지휘 (설계·기획·계획) | 메인 세션 | `main_model` (기본 `claude-opus-5-5`, `.claude/settings.json`의 `model`) | 전체 |
| 구현 | `.claude/agents/implementer.md` | `worker_model` (기본 `claude-sonnet-5-5`) | Read, Edit, Write, Bash, Grep, Glob |
| 검토 | `.claude/agents/code-reviewer.md` | `worker_model` | Read, Grep, Glob, Bash(훅으로 읽기 전용 명령만 허용) |

- 두 서브에이전트 모두 `Agent` 도구가 없어서 다른 서브에이전트를 부를 수 없다.
- 리뷰어(검토)와 수정 담당(implementer)을 분리했다. 리뷰어가 수정 권한까지 가지면 검토와 수정의 책임이 섞이기 때문이다.
- 리뷰어의 Bash 제한은 `.claude/hooks/reviewer_bash_guard.py`가 강제한다. 공식 문서상 서브에이전트의 `tools` 필드로는 Bash를 명령 단위로 제한할 수 없기 때문이다. 훅의 허용·차단 동작은 `tests/harness/test_reviewer_bash_guard.py`로 검사한다.
- 모델은 별칭(`sonnet`) 대신 고정 ID를 쓴다. 별칭은 새 모델이 나오면 가리키는 대상이 바뀌어 결과를 비교할 수 없다.

## 운영 중 변경 이력
- 2026-11-10: 첫 적용 프로젝트에서 새 세션으로 점검한 결과, 위임·모델·훅 차단은 의도대로 동작했다. 다만 당시 Claude Code 빌드에는 Grep·Glob 도구가 없어 리뷰어가 쓸 수 있는 도구가 Read와 Bash뿐이었다. 그래서 훅 허용 목록에 `ls`와 `grep`을 추가했다.
  - `grep` 재귀 검색은 차단한다. 권한 deny 규칙은 `grep -r pattern .`처럼 파일 이름을 직접 지정하지 않는 읽기를 막지 못하기 때문이다(공식 문서 기준). 재귀 검색은 `.gitignore`를 따르는 `git grep --untracked`로 대신한다.
  - `ls`·`grep` 인자에 `.env`, `secrets/`, `*.pem`, `*.key`가 들어가면 차단한다. `.env.example`은 허용한다. `-f.env`처럼 옵션에 붙인 경로도 차단한다.
  - `find`는 `-delete`, `-exec`로 파일을 바꿀 수 있어 계속 차단한다.
  - 알려진 오탐: `grep secrets app.py`처럼 검색어가 `secrets`나 `.env`이면 경로로 보고 차단한다. 이런 검색은 `git grep`으로 한다.

## 기대 효과 (가설)
- 설계 판단은 상위 모델이, 반복 구현은 비용이 낮은 모델이 맡아 작업당 비용을 줄인다.
- 구현과 검토의 맥락을 분리해 메인 세션의 맥락 소모를 줄이고, 구현자가 놓친 결함을 리뷰어가 찾는다.

## 측정할 지표
| 지표 | 수집 방법 |
| --- | --- |
| 리뷰어가 찾은 결함 중 실제 결함 비율 | 메인 세션이 지적 사항마다 수용·기각을 판정해 기록 |
| 리뷰 후에 발견된 결함 수 | 머지 후 버그·회귀로 발견된 건수 |
| 수정·재검토 반복 횟수 | 작업마다 기록 (상한 2회) |
| 작업당 토큰·비용 | 세션 사용량 기록 |
| 설계 위반으로 implementer가 멈춘 횟수 | implementer 보고서 |

## 한계
- 도입 전 Baseline(단일 모델로 구현·검토)이 없다. 비교가 필요하면 유사 난이도 과제 몇 개를 단일 세션 방식으로도 수행해 비교한다.
- 리뷰어 훅은 허용 목록 방식이라 새 검사 명령(pytest 등)이 생기면 허용 목록에 추가해야 한다.

## 재검토 트리거
- 리뷰 지적의 대부분이 기각되거나, 리뷰 후 결함이 줄지 않을 때
- 위임 왕복 때문에 단순 작업의 소요 시간이 눈에 띄게 늘 때
- 리뷰어가 테스트를 직접 실행해야 할 필요가 생길 때
